从并行计算到 Tile-Level 编程：CUDA、Triton 与 TileLang

2026-11-25- 2026-11-27
技术笔记-并行计算GPUCUDATritonTileLangSIMT

并行计算的核心问题只有一个：把一个计算任务切给更多计算单元，并让它们真正同时工作。围绕这个问题，硬件给出了不同的并行形态，编程模型给出了不同的抽象层次，而 GPU 编程近二十年的演进，就是逐步把「怎么切、怎么搬数据、怎么映射到线程」从程序员手里交给编译器。

本文沿一条自底向上的线索展开：计算与性能指标 → 可并行性与任务切分 → Flynn 分类与编程模型 → CUDA 执行模型与内存层次 → Tile-Level DSL（Triton / TileLang）。

计算的本质，以及「性能」的两个坐标

计算是把输入按特定规则转换为输出的过程：加减乘除、乘方开根、指数对数、比较、矩阵乘法，都是规则。落到机器上，规则由计算单元执行，输入输出对应数据搬运；程序则是处理器执行的一连串指令流。

一条指令的生命周期是：取指 → 译码 → 执行 → 访存 → 写回，时钟周期是执行指令的基本单位。衡量「算得快」有两个不同坐标：

指标 定义 靠什么提升
延迟 Latency 单个任务从开始到结束的时间 更强的单计算单元、更高的频率
吞吐 Throughput 单位时间内完成的总计算量 更多计算单元、更高的并行度

IPC（Instructions Per Cycle）衡量单周期执行指令数；IPC > 1 即超标量。当单个计算单元无法再快时，唯一的路是把计算单元数量堆起来 —— 这就是并行化，而并行度决定了能堆到什么程度。

什么样的计算可以并行

先看数据依赖。Bernstein 条件给出的判据是：两段计算的读集与写集互不冲突时，它们可以并行执行。

真正把并行写对的难点并不在「能不能并行」，而在并行之后：竞态与互斥锁、线程间通信与同步。科学计算（气候、物理、生物模拟）、矩阵计算与逐元素计算天生并行度高，深度学习正好落在后一类。

怎么切：三种分解方式

方式 思路 典型例子
Domain Decomposition 按数据切分，每个单元处理一块数据 矩阵分块、图像分块、网格划分
Functional Decomposition 按功能切分，每个单元负责一类任务 流水线中不同阶段各管一件事
流水并行 / 指令级并行 让不同阶段或不同指令重叠执行 指令流水、生产者—消费者管线

切分的目标只有一个：充分并行化，打满并行度，让所有计算单元都有活干。

硬件怎么并行：Flynn 分类

按「指令流 × 数据流」是否单一，可以把并行计算机分成四类：

分类 指令流 数据流 对应硬件
SISD 单 单 传统单核 CPU
SIMD 单 多 向量单元、昇腾 NPU
MISD 多 单 少见，多用于对同一数据做多种处理
MIMD 多 多 现代超算、多核 CPU、GPU

GPU 之所以难写，正因为它同时带有 SIMD 式的执行单元和 MIMD 式的调度层次。

程序员看到的并行模型

模型 关键点
Shared Memory (without threads) 多进程共享同一地址空间
Threads 显式线程，配合锁与同步
Distributed Memory / Message Passing 显式收发消息，MPI 是代表
Data Parallel / PGAS 数据分块 + 分区全局地址空间
Hybrid 上述模型组合
SPMD 同一份程序处理不同数据（MPI、OpenMP 常见）
MPMD 不同程序处理不同数据

再往下还有两层更贴近硬件的视角：

  • SIMT 与 CUDA：以线程为「组成」单位，自下而上地组装并行，属于 Thread Level Programming。
  • Tile 模型与 DSL：以数据块为「拆分」单位，自上而下地描述计算，属于 Block / CTA Level Programming。

理解一个并行系统，可以交替使用三种视角：关注数据与指令的体系结构视角（SIMD、SIMT）、关注如何描述计算的编程模型视角（SPMD、Tile）、以及第一性原理层面的自上而下 / 自下而上拆解。

这些并行落在 AI 系统哪里

算子、集群通信、分布式训练、强化学习系统、推理框架，本质上都在解决同一组问题：切分、搬运、同步、重叠。只是层次不同 —— 算子层关心一个 tile 怎么算，通信层关心跨设备怎么搬，框架层关心计算和通信怎么重叠。

为什么是 GPU：三个理由

一胜：控制与计算的比例。 CPU 面向「大量控制、少量计算」，GPU 面向「少量控制、大量计算」。把晶体管预算从分支预测、乱序控制转移到算术单元，吞吐自然更高。

二胜：不降低延迟，而是隐藏延迟。 GPU 标称的算力是吞吐量；对硬件厂商来说，提高吞吐比降低延迟容易得多。int32 加法在 CPU 上是 1 个时钟周期，在 GPU 上是 4 个时钟周期 —— GPU 并不擅长降低延迟，它的思路是「同时处理足够多的任务，让计算单元等待数据时总有别的活干」。

三胜：显存带宽。 GPU 主存通常是 HBM，一条 HBM3E 的带宽可以达到 DDR5 的 20 倍。但带宽有前提：必须做地址连续的大块访问（coalesced access），随机小粒度访问会把带宽浪费掉。

这三条合起来是一句设计哲学：用并行度和带宽换吞吐，而不是用频率换延迟。

CUDA 的层次结构

2006 年出现的 CUDA，让通用计算负载可以脱离图形 API 直接使用 GPU 的吞吐能力。它的核心概念是自下而上的：

概念 含义
thread 程序运行的基本单元
warp 32 个 thread，执行相同指令
block / CTA Cooperative Thread Array，线程间合作的范围
SM Streaming Multiprocessor，执行 block / warp 的硬件
grid block 的集合

关键性质是自动可扩展性：每个 block 都是可独立执行的程序，block 之间没有数据依赖，可以按任意顺序调度到任意数量的 SM 上。因此 block 数量可以远多于 SM 数量，调度顺序未定义，程序员不需要关心设备总共有几个 SM，也不需要为不同型号的卡重新编译或改代码。

从 .cu 到可执行文件

阶段 产物 说明
源码 .cu CUDA 扩展了 C/C++ 语法
编译 nvcc 分离 host / device 代码
中间表示 PTX Parallel Thread eXecution，类似「高级汇编」，后向兼容性较好
机器码 CUBIN GPU 上的可执行文件

一次典型调用分五步：在 CPU 上准备数据 → 把数据从 CPU 内存拷到 GPU 内存 → 配置 kernel 启动参数 <<<grid, block>>> → 在 GPU 上并行执行 kernel → 把结果拷回 CPU 内存。

多 block 与边界处理

矩阵大小经常不是块长的整数倍，处理方式就是加一个边界判断：

Warp、SIMT 与 SIMD

一个 warp 是 32 个必须执行相同指令的 thread。出现分支时，分支路径会串行化：走当前路径的线程被激活，其余线程被 mask 掉。

  • SIMD：Single Instruction Multiple Data，数据被动，只有一个 program counter。
  • SIMT：Single Instruction Multiple Thread，线程主动；从 Compute Capability 7.0 起每个 thread 有自己的 program counter，理论上可以执行不同指令。

但同一个 warp 里每次激活的 thread 仍应有相同的 program counter。条件分支太多会导致 program counter 取值太分散，SIMT 也随之低效 —— 最有利于 SIMT 发挥效率的写法，仍然是 SIMD 式的规整控制流。

Warp divergence 的优化方向很直接：让数据分布与 warp 边界对齐，尽量使 warp 内所有线程走同一分支。

Block 内协作与 Thread Block Cluster

block 内的 thread 类似 CPU 线程，可以用 shared memory，也有原子操作、内存屏障、__syncthreads() 等同步指令。从 Compute Capability 9.0 起增加了一个可选的中间层次 Thread Block Cluster：cluster 中的 block 保证在同一个 GPC（Graphics Processing Cluster）上调度，因而可以实现跨 block 通信。

内存层次与合并访存

层次 作用域 特点
Register 单个 thread 私有 访问最快
Shared Memory block 内共享 与 L1 Cache 是同一块物理存储的不同划分，比例可配置；用于数据复用
L1 / L2 Cache SM / 全片 L1 缓存行 128 字节，L2 缓存行 32 字节
Global Memory 所有 block 可访问 容量大、延迟高

共享内存优化的经典例子是分块矩阵乘法：把 A、B 的 tile 先搬进 shared memory，再在 block 内复用，__restrict__ 与转置等技巧用来减少重复加载与 bank conflict。

全局内存访问效率取决于访问模式。GPU 会把 warp 中 32 个线程的访存请求合并为尽量少的 transaction；一次 transaction 是 32 字节，起始地址是 32 字节的倍数。这类似 CPU 的缓存行机制，但层次更复杂：地址连续的大块访问才能打满带宽，随机小粒度访问会浪费带宽。

SM 内部与 warp 调度

以 Blackwell Ultra 为例，一个 SM 内有 128 个 CUDA Cores 用于 32 位及更低精度计算，另有 SFU（近似倒数、平方根倒数、sin 等特殊函数单元）与 Tex（纹理单元）。

核心矛盾是：CUDA Core 运算极快，而 Global Memory 延迟是几百个周期。如果一个 warp 发出访存请求就干等，计算单元立刻空闲。解决办法是 warp 调度器维护远多于计算单元的 warp：

  • 一个 warp 因访存阻塞，调度器立即切换到另一个可执行 warp；
  • 硬件维护所有 warp 的寄存器状态，上下文切换开销很低；
  • 计算单元与内存带宽因此都能尽量保持满负载。

一句话：用吞吐量掩盖延迟。

Occupancy

高 occupancy 有助于隐藏延迟，但 SM 的资源是有限的：寄存器、shared memory、最大 warp 数都会限制同时驻留的 warp。寄存器压力（register pressure）是很多 kernel 的关键问题，__restrict__ 这类受限指针的使用反而可能因降低 occupancy 而拖慢性能。因此调块长不是拍脑袋：要在 block 大小、寄存器用量、shared memory 用量之间找平衡点。

优化方向清单

  • 最大化并行执行：足够的 thread / block，用满全部 SM。
  • 优化内存访问：合并访问、使用 shared memory 做数据复用。
  • 最小化 warp divergence：保持 warp 内控制流一致。
  • 利用专用硬件：Tensor Core 等专用单元。

为什么需要 Tile-Level 编程

手写 CUDA 时，程序员要显式指定：每个 block 和 thread 的分工、数据在 Global / Shared / Register 之间的搬运、从「数据分块」到「线程执行」的完整映射。线程协作、数据复用、shared memory 全靠手工管理，写起来繁琐、容易出错、难以优化。

Tile-Level 的思路是把 block 内线程的协作抽象成分块（tile）操作，由编译器负责把 tile 操作映射到具体线程。一个 tile kernel 的固定套路是：

  • 确定当前 tile 的位置；
  • 从 global memory 加载 tile；
  • 对 tile 做计算；
  • 把结果写回 global memory；
  • 处理边界。

Triton 与 TileLang 是这个思想的两种 DSL 表达。

Triton：从 Program 出发

CUDA kernel 从 thread 出发，显式计算每个线程负责的数据；Triton kernel 从 program 出发，每个 program 负责一个数据 tile。程序员描述 tile 的位置、形状以及 load / compute / store，编译器负责把 tile 内计算映射到 thread 与 warp —— 保留数据分块的决策权，交出线程级映射。

Triton 的局限：编译器是黑盒，shared memory 布局与 bank conflict 全靠编译器；生成的 PTX / SASS 不透明，性能问题难定位；距 CUTLASS / cuBLAS 手工优化仍有性能天花板；复杂 pipeline、warp specialization 难表达；复杂 kernel 写起来别扭，报错与性能回退依赖反复 autotune。本质上是用放弃部分控制权换开发效率。

TileLang：显式写出内存层次

当控制权本身成为瓶颈，就需要更贴近 kernel 结构的表达。TileLang 强调显式写出层次：

层次 对应概念
kernel / program kernel 入口，一个实例对应一个 CTA
global memory 输入输出张量所在显存
shared memory tile CTA 内共享的缓存块
register fragment 寄存器中的计算结果
loop over tiles 沿某维度分块循环

三者怎么选

方案 特点 适合
Triton 快速写出简洁 kernel elementwise、reduction、matmul、attention
TileLang 显式表达内存层次与数据复用 讲清高性能 kernel 的结构、需要精细控制数据流
CUDA C++ 控制粒度最细 极端性能调优、特殊硬件机制

一条自底向上的主线到这里闭合：从「延迟 vs 吞吐」出发，经过 Flynn 分类与 SIMT 执行模型，到内存层次、合并访存与 occupancy，最后把线程级细节交给编译器，回到「数据分块」这一最上层的决策。
