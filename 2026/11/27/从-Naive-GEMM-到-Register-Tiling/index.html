从 Naive GEMM 到 Register Tiling：FP32 矩阵乘法的逐级优化

2026-11-27
技术笔记-GPUCUDACoalescingGEMM矩阵乘法Shared MemoryRegister TilingMIO

矩阵乘法是少数能把一个 kernel 从「带宽受限」一路推到「算力受限」的算子：计算量随规模立方增长，数据随平方增长，天然存在大量复用机会。但复用不会自动发生 —— 它要靠拆分方式、内存层次和指令发射一层层设计出来。本文沿 FP32 GEMM 的完整优化路径，从每个线程算一个输出元素开始，走到寄存器分块、MIO 队列瓶颈，以及最后仍然卡在 load 上的那一段流水线。

矩阵乘法与优化目标

优化目标是 FLOP/s，基本运算是 FMA（一次乘加计 2 FLOP）。并行化的本质是拆分计算和数据：把 C 的不同元素分给不同线程，沿 K 维做累加。最直接的拆法就是数据并行 —— 每个 thread 负责一个输出元素。

最朴素的拆分：每个 thread 一个 C 元素

逻辑清晰、边界判断简单，但每个线程都独立地把一整行 A 和一整列 B 从全局内存读一遍。

瓶颈在数据复用，不在算力

  • 4 个相邻线程计算 4 个输出，却只依赖 2 行 A 和 2 列 B —— 复用机会完全没有被利用。
  • 每个线程访问 2K 个输入和 1 个输出，做了 K 次 FMA。
  • 算术强度（每个 float 按 4 字节计）：
  • 理想的大规模匀称 GEMM 是 compute bound 的：

由 Roofline 看得很清楚：0.25 远在脊点左侧，性能被带宽锁死。要往上走，必须把 A、B 的复用从「碰巧被 cache 接住」变成「代码里显式组织出来」。

Shared memory tiling：让 CTA 显式协作

Cache 可能捕获一部分复用，但代码没有显式组织、也无法保证这种协作。改用 2D CTA grid，让每个 CTA 负责一个 BM × BN 的输出 tile；这一次由 threads 协作把需要的数据搬进 shared memory，再在块内复用。

两次同步各自守住一个正确性边界：写后读、读完再覆盖。此时算术强度提升为：

从 0.25 到 8，是 32 倍的理论复用提升，kernel 终于有资格向算力上界靠拢。

Global → Shared 的合并访存

共享内存分块之后，全局内存到共享内存的这一段搬运必须合并：

  • 逻辑上的高维 thread 和矩阵，对应的硬件执行和内存地址总是 1D 的。
  • C 风格数组是 Row-major：A[i][j] = A[i * K + j]，连续变动的是最后一维。
  • CUDA 的线程编号约定：linear_tid = tx + blockDim.x * ty，threadIdx.x 是变化最快的维度。
  • 一个 warp 的 32 个 FP32 恰好是 128 有用字节，对应 4 个对齐 sector。

如果让 lane 去对应矩阵的行（跨步访问），就会出现 mismatch：同一条指令散落到更多 sector，搬运被放大。正确做法是对齐最连续的维度 —— 让 tx 沿 K 方向连续，A 的行内、B 的列内都保持连续地址。

向量化搬运

合并之外，还可以把一次 load 的粒度从 4 字节抬到 16 字节：

contiguous, aligned memory access 让一个 warp 的连续请求落在整齐的 cache line 上：指令数减少到四分之一，单次请求字节数翻 4 倍，也为后续流水线留出更多在飞数据。

瓶颈转移：Shared Tiling 不等于持续发射

再看调度层面：Scheduler 手上有足够多的 resident warps，但大多数周期没有 eligible warp。原因不在 occupancy，而在 MIO / shared-memory instruction pressure。

Warp Scheduler 下游大致分三类路径：

路径 承载的指令
FMA / math pipelines 浮点乘加等算术指令
global / local-memory paths 全局与本地内存访问
MIO queue shared-memory instructions、special math、dynamic branch-related operations

warp 想继续发 shared / MIO 指令，但相关 instruction queue 已经拥塞；指令统计里绝大多数都是 load/store。也就是说：数据复用还不够，绝大多数指令都花在把数据搬来搬去上。出路是让每个线程用一次 shared load 算出更多输出。

Register Tiling：让每个线程算更多输出

不再让一个 thread 只算一个 C 元素，而是让它在寄存器里维护一小块累加器：

关键参数与每轮工作量：

项 值
CTA tile 32 × 32
Thread tile 2 × 2
Thread grid 16 × 16 = 256 threads
每个 k 步 2 个 A 值 + 2 个 B 值 → 4 次 FMA

收益有两层：

  • tile 内每个 thread 处理更多输出元素，shared-load instruction pressure 下降，同时把一部分线程从搬运里解放出来；
  • 线程不再被「一个输出元素」绑死，CTA tile 可以做更大，而 AI = BM·BN / (2(BM + BN)) 随 tile 增大继续提高 data reuse。

达到的水平与剩余瓶颈

沿这条路径走下来，实测可以达到：

  • 80%+ cuBLAS performance；
  • 87% fp32 pipe util。

但流水仍是串行的：

Load 依旧占据关键时间。下一步是把搬运和计算解耦：

  • 多缓冲（Stages）：拉长计算依赖距离，让下一轮数据在上一轮计算时就已经在路上；
  • 异步数据搬运：cp.async 把 global → shared 从同步发射里摘出来；
  • Tensor Memory Accelerator：用专用异步硬件承担 bulk 搬运，把 warp 留给算术。

优化阶梯小结

阶段 手段 关键指标或瓶颈
每线程一元素 数据并行 AI ≈ 0.25 FLOPs/Byte，受带宽约束
Shared tiling CTA 协作搬运 As/Bs AI = 8 FLOPs/Byte（T=32）
Coalescing / 向量化 row-major 对齐 + float4 32 FP32 = 128 B = 4 sectors
Register tiling TM×TN = 2×2 寄存器累加 降低 MIO / shared-load 压力
多缓冲 / 异步搬运 Stages、cp.async、TMA 打破串行 load → compute

一条贯穿始终的判据是：先算清楚算术强度，再看指令队列里到底堵的是算术还是 load/store。GEMM 的每一次跃升，都是把「数据搬几次」换成了「搬一次能算多少」。
