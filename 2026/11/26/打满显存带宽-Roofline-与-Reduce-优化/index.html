打满显存带宽：Roofline、Little's Law 与 Reduce 的七级优化

2026-11-26- 2026-11-27
技术笔记-GPUCUDA内存层次RooflineOccupancyCoalescingWarp ShuffleReduce

一个 kernel 到底能跑多快？答案不在「代码写得多巧」，而在一个上界：算力峰值、显存带宽，以及你的访存模式离这个上界有多远。本文从 Roofline 出发，用 Little’s Law 解释「为什么必须让足够多的数据同时在飞」，再沿着一个 Reduce kernel 的七级优化，把 coalescing、occupancy、向量化、bank conflict、warp shuffle 这些概念逐一落到具体的数字上。

Roofline：先判断被什么卡住

性能上界由两条线决定：

  • P_peak：算力峰值，水平线。
  • BW × I：带宽线，斜率就是显存带宽。
  • I：算术强度（Operational Intensity），单位 FLOPs/byte，即每从 DRAM 读一个字节能做多少计算。
  • 两条线的交点是脊点 I* = P_peak / BW。

在 Roofline 图上，脊点左侧的应用（低算术强度）无论怎么优化算力都受带宽约束；右侧的应用才可能触到算力天花板。图上三个典型点很直观：I = 4 的应用落在斜线下方，I = 16 的应用刚过脊点却远离峰值水平线，I = 512 的应用仍然受峰值限制 —— 算术强度决定你在哪条线上，实现质量决定你离那条线多远。

绝大多数逐元素算子、归约、拷贝类 kernel 的算术强度极低，属于 memory-bound。对它们而言，优化目标只有一个：把有效带宽打到接近硬件标称值。

一个「理想带宽 kernel」的前提

要打满带宽，需要同时满足五个条件：

  • 完美合并访存（coalesced）；
  • 没有 warp divergence，没有同步停顿；
  • 100% occupancy；
  • 任务 embarrassingly parallel，没有数据依赖；
  • 每个内存请求都足够大、足够连续。

现实中的 kernel 总是缺其中几条。后面所有优化，本质上是在逐项逼近这个理想状态。

Little’s Law：为什么光有带宽不够

先看一个类比：一段有 20 个台阶的楼梯，每个台阶站 1 个人，走一个台阶要 2 秒。

  • 吞吐：0.5 人/秒；
  • 单个乘客从底到顶的延迟：20 × 2s = 40s；
  • 要占满吞吐，必须同时有 带宽 × 延迟 = 0.5 × 40 = 20 人 在楼梯上。

内存系统完全一样：

带宽是「每秒能搬多少」，延迟是「一次请求多久回来」；只有把足够多的请求同时挂在流水线上，带宽才吃得满。这就是 Little’s Law L = λW 在显存上的形式。

用真实硬件算一遍：

指标 A100 80GB H100 SXM B200
内存带宽 B 1.94 TB/s 3.35 TB/s 8 TB/s
DRAM 延迟 L 500 ns 600 ns 650 ns
全 GPU 在飞字节 B×L 1.0 MB 2.0 MB 5.2 MB
SM 数量 108 132 148
每 SM 需要 9 KB 15 KB 35 KB
每 SM 最大驻留线程 2048 2048 2048
每线程需要 4.7 B 7.4 B 17 B

结论很硬：在 B200 上，每个线程必须平均维持 17 字节在飞，才能喂满 8 TB/s。只让一个线程发一个 4 字节的 load，无论启动多少个 block，都填不满这条流水线。这直接引出两个手段 —— 足够的 occupancy 和 每线程多element / 向量化加载。

Occupancy：用足够多的 warp 填满延迟

一个 SM 内部有 4 个 SMSP（SM 子分区），每个都有独立的 warp scheduler，每个 cycle 从 eligible 的 warp 里挑一个发射；每个 SMSP 最多驻留 16 个 warp。

限制 occupancy 的资源是硬性的：

资源 每 SM 上限
Shared memory 164 KB（A100）、228 KB（H100 / B200）
寄存器 65536 个 32-bit 寄存器

寄存器用量、__shared__ 数组大小、block 大小三者共同决定能同时驻留多少 warp。寄存器压力上升 → occupancy 下降 → 在飞请求数下降 → 带宽打不满。所以「把块长调大」不是直觉问题，而是在 blockDim、regs/thread、smem/block 之间解一个约束方程。

值得注意的是：高 occupancy 不是目的，足够的在飞字节数才是。当一个 kernel 靠向量化加载让每个线程维持多字节在飞时，即使 occupancy 略低也能打满带宽。

让每个线程多搬一点：grid-stride、展开与向量化

grid-stride + 循环展开

让每个线程用 grid stride 处理 2 个元素，并展开循环：

时序图上，两个元素的 load 被提前发射，第一组 load 与 FMA 之间形成 20 字节在飞，第二组 8 字节，最后 4 字节；总周期 2011，做到 2 倍的工作量只用 2 倍周期 —— 关键不是省了周期，而是把原本空等的延迟槽填上了独立请求。

向量化访存

float4 让一条指令搬 16 字节（cudaMalloc 的分配天然满足 16 字节对齐）：

收益有三层：指令数减少到 1/4、每次请求 16 字节更接近 sector 粒度、单个线程的在飞字节数直接翻 4 倍。这正是上一节 Little’s Law 里「每线程 17 B」那种需求的解法。

合并访存：sector 是最小计费单位

内存访问不是按字节计费，而是按 sector：

规则 数值
最小访存粒度 32 bytes = 1 sector
L1 → L2 1 sector
L2 → Global 2 sectors（默认；cudaDeviceSet... 可设 preferred granularity，但只是 hint）
Cache line 128 bytes = 4 sectors
Cache 管理粒度 1 cache line（请求合并、逐出都按此粒度）
对齐要求 128-byte alignment

一个 warp 的 32 个线程各读一个 4 字节 float，若起始地址对齐且连续，正好落在 4 个 sector；若起始地址偏移（例如从 160 开始读到 288），则要触碰 5 个 sector，多付 25% 的带宽。图示里 32 条斜线跨过 5 个绿色 sector，就是这个浪费。

所以访存优化的判据非常直接：让 warp 内 32 个 lane 的地址连续、起始 128 字节对齐、避免跨步和随机小粒度访问。

Shared memory 的 bank conflict

Shared memory 被分成 32 个 bank，4 字节宽度交织编址。同一条指令里，若多个线程命中同一 bank 的不同地址，请求会串行化：

访问模式 代码 结果
连续访问 shmem[threadIdx.x] = data[tid] 无冲突
跨步访问 shmem[threadIdx.x * 2] = data[tid] 2-way bank conflict
广播访问 data = shmem[0] 无冲突（广播是特例）

在归约类 kernel 里，s[tid] + s[tid + stride] 的步长会让不同线程落到同一 bank；分析工具会显示 shared load 平均 3.5-way bank conflict、L1/TEX wavefronts 上升、shared 吞吐下降。规避手段是 padding、swizzle 或换一种索引映射 —— 本质都是把「同一 bank 的不同地址」拆开。

案例：Reduce 的七级优化

下面这组数字是同一个归约任务从最朴素写法一路优化到接近 HBM 带宽上限的完整阶梯：

版本 关键改动 时间 有效带宽 相对加速
v1 每线程 atomicAdd 到全局内存 197 ms 1.4 GB/s —
v2 搬进 shared memory，交错折半归约 1.67 ms 160 GB/s 118×
v3 改连续索引，消除 warp divergence 0.87 ms 308 GB/s 1.9×
v4 从 blockDim.x / 2 起折半，减少无效线程与同步 0.78 ms 344 GB/s —
v5 grid-stride 每线程累加多元素，gridDim = SM 数 × 16 0.25 ms 1074 GB/s —
v6 warp shuffle 两级归约替代 shared memory 0.247 ms 1087 GB/s —
v7 float4 向量化加载 + warp 归约 0.17 ms 1572 GB/s —

v1：全局原子加

所有线程争抢同一个全局地址，原子操作串行化，带宽只有 1.4 GB/s。问题不在带宽，而在把并行任务压成了一个串行瓶颈。

v2：shared memory + 交错折半

118 倍加速来自把 N 次全局原子操作收敛成「每 block 一次」。但 tid % (2*stride) == 0 让同一个 warp 内只有部分 lane 活跃，控制流发散、shared 访问也不连续。

v3：连续索引消除 divergence

活跃线程变成连续的 tid < blockDim.x / (2*stride)，warp 内控制流一致，带宽从 160 提到 308 GB/s。

v4：从大到小折半

这是最经典的树形归约：第一轮就让一半线程干活，同步次数相同但每轮的有效 warp 更集中。此时分析指标为：Compute (SM) Throughput 62.22%、Memory Throughput 70.38%、L1/TEX Cache Throughput 72.44%、L2 Cache Throughput 18.93%、DRAM Throughput 18.01% —— DRAM 只用了 18%，说明瓶颈还在访存组织和同步，不在显存本身。

v5：grid-stride 累加 + 固定 grid 规模

关键改动是启动参数：

不再为每个数据元素各开一个 block，而是开「刚好喂满所有 SM」的持久化 block，每个线程用 grid-stride 循环累加多个元素。启动开销、block 调度开销、原子操作次数同时下降，带宽直接跳到 1074 GB/s。这正是Little’s Law 的兑现：让每个线程维持多个在飞请求。

v6：warp shuffle 两级归约

折半归约到 stride ≤ 16 时，参与的线程全在一个 warp 内；32 个 lane 可以直接交换寄存器，不必再经 shared memory 和 __syncthreads()：

只剩一次跨 warp 的 shared memory 中转和一次同步，0.247 ms / 1087 GB/s。

v7：向量化加载收尾

一次 load 拿 4 个 float，配合固定 grid 规模与 warp shuffle，最终 0.17 ms / 1572 GB/s。从 197 ms 到 0.17 ms，约 1159 倍；从 1.4 GB/s 到 1572 GB/s，约 1123 倍。

Warp Shuffle 原语

指令 lane i 接收 用途
__shfl_sync(mask, var, srcLane, width) 指定的 srcLane 广播 / 置换
__shfl_up_sync(mask, var, delta, width) i - delta Prefix sum、stencil
__shfl_down_sync(mask, var, delta, width) i + delta Reduce（结果落在 lane 0）
__shfl_xor_sync(mask, var, laneMask, width) i xor laneMask Butterfly Reduce（所有 lane 都拿到结果）

两种归约形态：

两个容易踩坑的参数：

  • mask：0xffffffff 表示全部 32 个 lane 参与；分支导致 lane 与 mask 不符时是未定义行为，收敛的 warp 用 __activemask() 取实际活跃集合。
  • width：默认 32（warpSize）；设为 8 时把一个 warp 切成 4 段，每段 8 个 lane 在段内交换，适合「每 8 个 lane 处理一行」这类布局。

从 1087 到 1572 GB/s 做对了什么

最后一级没有引入新硬件特性，只是把前面所有原则叠满：

  • float4 让每线程在飞字节数翻 4 倍（Little’s Law）；
  • 固定 gridDim = SM 数 × 16，避免过量 block 调度；
  • warp shuffle 替掉 shared memory 与同步，减少 stall；
  • 地址 16 字节对齐且连续，sector 利用率最高；
  • 每线程累加多个元素，用 ILP 而不是 occupancy 去填延迟。

所以这不是「某个神奇指令把速度提上去」，而是把每一处带宽浪费逐个消掉：原子争用 → 全局访存次数 → divergence → 无效同步 → 启动规模 → shared memory 中转 → 单次请求粒度。

优化检查清单

检查项 判据 手段
是否 memory-bound 算术强度低于脊点 P_peak / BW 提高数据复用，或减少 DRAM 往返
在飞字节数够不够 带宽 × 延迟 与每线程在飞字节对比 grid-stride、循环展开、向量化加载
occupancy 是否受限 活动 warp / 最大 warp 控制寄存器与 shared memory 用量，调块长
访存是否合并 warp 请求落在几个 sector 地址连续、128 字节对齐、避免跨步
shared 是否有 bank conflict 分析工具的 wavefront / conflict 指标 padding、swizzle、换索引映射
是否还在用全局原子操作收敛 原子操作次数 ≈ block 数？ block 内先归约，每 block 一次原子
是否还在用 __syncthreads() 做 warp 内归约 stride ≤ 16 换成 warp shuffle
启动规模是否过大 gridDim ≈ ceil(n / blockDim) 固定为 SM 数 × 每 SM 目标 block 数
单次 load 是否太细 每线程 4 字节 float4 / int4 向量化
