Claude Code 任务运行时：从临时计划到持久任务、后台执行与定时调度

2026-07-15- 2026-07-31
3.8k- 15m
课程笔记-学习Agent大模型Claude Code

本文是 Learn Claude Code 学习笔记的第三篇。前两篇讲了单 Agent 的六个核心机制和五种耐久性加固。这一篇讲怎么把工作从「会话内的临时计划」升级成「可持久化、可后台执行、可定时触发」的任务执行系统。

为什么需要任务运行时

前两个阶段结束时，Agent 已经能循环、会用工具、有权限、有 Hook、有技能、有压缩、有记忆、有错误恢复。但它的任务管理还停留在 s05 的 todo_write：一个保存在会话内存里的列表，会话一结束就没了。三个具体问题：

  1. 任务之间有先后依赖（先建数据库表再写 API），但 todo 列表是平铺的，没有依赖关系
  2. 慢操作（npm install、pytest、docker build）会阻塞主循环，Agent 在等待期间什么都做不了
  3. 有些工作不是现在做，而是将来某个时间做（每天跑测试、30 分钟后提醒），但没有调度的能力

这三章依次解决这三个问题。核心一句话：三者最终都汇入同一条主循环，不是各开一条新循环。

任务系统：持久化的目标图

问题在哪

Agent 接到一个项目：搭数据库、写 API、加测试。它用 todo_write 列了清单，然后开始写 API，写到一半发现没数据库表，回头补；加测试时发现 API 接口签名又变了。

盖房子不能先盖屋顶再打地基。任务之间有先后，任务依赖应该形成有向无环图（DAG）。而且 s05 的 todo 是会话内存里的，会话一结束就没了，昨天做了一半的工作今天没法接着做。

关键名词

Task（任务）：不再是一行字符串，而是一个有 id、有依赖、有 owner、能落盘的目标单元。

blockedBy（依赖）：一个任务只能在它依赖的所有任务全部 completed 之后才能开始。多个 blockedBy 自然组成一张 DAG。

持久化：任务状态不靠进程内存，而是写在 .tasks/ 目录的 JSON 文件里。进程崩了、会话关了，下次重新读文件就能恢复进度。

整张图可以这样理解：

schema 没有依赖，可以立刻开始；endpoints 和 docs 都 blockedBy schema，必须等它完成；tests 又依赖 endpoints。完成 schema 会自动「解锁」下游的 endpoints 和 docs。

数据结构

ID 用 timestamp + random hex 生成（task_{int(time.time())}_{random_hex(4)}），简单但够用。

状态机：

教学版没有 in_progress -> pending 的 release 路径。如果 Agent 中途退出，任务永远停在 in_progress（CC 会自动归还，见后面）。

实现

create_task：创建任务。创建时自动 save_task 到 .tasks/{id}.json：

can_start：依赖检查。一个任务只能在它的 blockedBy 全部 completed 之后才能开始。不存在的依赖视为 blocked，避免引用错误 ID 时崩溃：

claim_task：认领任务。设置 owner，状态从 pending 变 in_progress。两条拒绝路径分开看：任务已被别人认领，或者依赖没完成：

complete_task：完成与解锁。任务做完后设为 completed，同时扫描所有其他任务，找出刚刚被解锁的下游任务：

完成 schema 后，endpoints 和 docs 的 can_start 都返回 True，它们可以开始了。这条「完成即解锁下游」的反馈，让 Agent 每完成一步都清楚下一步能做什么。

合起来跑的完整流程：

每个 create_task 写一个 JSON 文件，每个 claim_task / complete_task 更新文件。跨会话时 .tasks/ 目录还在，Agent 读文件就能恢复进度。

Claude Code 真实实现的差异

不是 TodoWrite 的升级，是两个独立系统。CC 中 Task System 和 TodoWrite 同时存在，通过 isTodoV2Enabled() 切换：交互式会话默认启用 Task（V2），非交互式 / SDK 默认用 TodoWrite。Task 有 TodoWrite 没有的：文件锁并发保护、依赖强制执行、ownership、fs.watch 响应式监听、生命周期 hooks。

并发认领的锁机制。CC 的 claimTask() 用双重锁防竞争。任务文件锁：proper-lockfile 锁住 {taskId}.json（最多重试 30 次，指数退避 5 到 100ms）。锁内做四件事：重新读取任务（防 TOCTOU）、检查已被他人认领返回 already_claimed、检查已完成返回 already_resolved、检查上游未完成返回 blocked，最后设置 owner。列表级锁：原子性扫描所有任务并检查该 agent 是否已有其他 open task。

claim 和开始工作分开。教学版把 claim 和开始工作合成一步（claim = set owner + in_progress）；真实 CC 的 claimTask 主要解决 owner 竞争，只设 owner 不改 status，状态更新由 TaskUpdate 单独完成。

高水位标防 ID 重用。.highwatermark 文件记录曾分配过的最高任务 ID。即使任务被删除，ID 也不会被重用，避免引用悬空。

任务恢复路径。教学版没有 in_progress -> pending 的 release。CC 中如果 teammate 终止或 shutdown，会把未完成任务 unassign（清除 owner）并把 status 重置为 pending，方便其他 agent 重新认领。

四个独立工具。CC 有 TaskCreate、TaskGet、TaskUpdate、TaskList 四个独立工具（不是教学版的一个通用 Task 工具）。全部设置 isConcurrencySafe: true 和 shouldDefer: true，工具 schema 不在初始 prompt 中，需 ToolSearch 后才可见。

易错点

  1. 把任务系统当成 TodoWrite 的换皮：TodoWrite 是会话内清单，Task System 是跨会话持久化 + 依赖图 + ownership，两者解决的不是同一个问题
  2. blockedBy 引用了不存在的 ID：教学版视为 blocked（不会崩），但 Agent 会一直卡住
  3. 没有环检测：A 依赖 B、B 又依赖 A 会死锁。生产实现要加拓扑检查
  4. claim 和 complete 不成对：Agent 认领了任务但中途退出，任务永远停在 in_progress，下游永远 blocked

后台任务：让等待不再阻塞主循环

问题在哪

前面几章里，工具调用基本都是「模型发起 -> 立刻执行 -> 立刻返回结果」。这对短命令没问题。但一旦遇到慢操作（npm install、pytest、docker build）就会卡住：模型在等待期间什么都做不了，用户明明还想继续别的工作，却被整轮流程堵住。

核心概念

这一章最关键的句子：主循环仍然只有一条，并行的是等待，不是主循环本身。

数据结构

RuntimeTaskRecord（正在运行的执行单元）：

落盘建议两份文件：.runtime-tasks/{id}.json 记录运行状态，{id}.log 保存完整产物。通知只负责把 preview 带回主循环。

Notification（通知）：

通知只负责一件事：告诉主循环「有结果回来了，你要不要看」。它不是完整日志本体。

实现

BackgroundManager 至少要有两块状态：tasks 是当前有哪些后台任务，notifications 是哪些结果已经回来等待主循环领取。

为什么完整输出不要直接塞回 prompt

如果后台任务输出几万行日志，每次都把全文塞回上下文，上下文很快就被撑爆。更稳的做法分三步：完整输出写磁盘（.log 文件）；通知里只放简短摘要（preview，建议 500 字符量级）；模型真的要看全文时再调用 read_file 主动读取。

背后的心智：通知负责提醒，文件负责存原文。

任务系统 vs 后台任务：最关键的区分

这是最容易混淆的地方：

s12 的 task 是「工作目标」。它关心的是：要做什么、谁依赖谁、现在总体进度如何。

s13 的 background task 是「正在运行的执行单元」。它关心的是：哪个命令正在跑、跑到什么状态、结果什么时候回来。

最稳的记法：task 更像工作板，background task 更像运行中的作业。两者相关，但不是同一个东西。混淆会让后面多 Agent 和调度章节全部打结。

易错点

  1. 以为「后台」就是更复杂的主循环：不是。主循环保持单主线，并行的是等待
  2. 只开线程不登记状态：任务一多就不知道谁还在跑、谁完成了、谁失败了
  3. 把长日志全文塞进上下文：通知只放 preview，全文写文件
  4. 把工作目标和运行任务混为一谈：Task 是目标，RuntimeTaskRecord 是作业

定时调度：让未来意图自动进入主循环

问题在哪

s13 让系统学会了把慢命令放到后台。但后台任务默认还是「现在就启动」。很多真实需求并不是现在做：每天晚上跑一次测试、每周一早上生成报告、30 分钟后提醒继续检查某个结果。

核心概念

这一章要加上的能力：把一条未来要执行的意图先记下来，等时间到了再触发。

定时调度并不是另一套 agent。它最终还是回到同一条主循环。

后台任务 vs 定时调度

一句话记法：后台任务是在「等结果」，定时调度是在「等开始」。

  • s13 后台任务：现在就开始做，只是结果稍后回来拿。它解决的是「等结果」。
  • s14 定时调度：现在不开始，将来某个时间才开始。它解决的是「等开始」。

易错点

  1. 沉迷 cron 语法细节：教学主线是「调度记录如何进入通知队列、又如何回到主循环」，不是背语法
  2. **没有 last_fired_at**：一分钟内被检查多次就触发多次
  3. 只放内存不支持落盘：程序一重启调度就没了。durable=True 时必须写文件
  4. 把调度触发结果直接在后台默默执行：教学主线里更清楚的做法是「时间到了先发通知再让主循环决定怎么处理」，避免绕过权限 / hook

小结：三层任务运行时

机制 解决什么问题 核心设计
任务系统 跨会话恢复 + 依赖管理 Task JSON 文件 + blockedBy DAG + .tasks/ 目录
后台任务 慢操作阻塞主循环 异步执行线 + 通知队列，主循环不陪等
定时调度 未来时间触发的意图 ScheduleRecord + 每分钟 cron 检查 + 通知队列回流

三者的共同特征：都通过通知队列回到同一条主循环。任务系统负责「记住要做什么」，后台任务负责「让等待不再阻塞」，定时调度负责「让一条未来意图在合适时刻自动进入主循环」。主循环始终只有一条。

这三章完成后，主循环现在能接收三类外部事件：用户输入、后台完成通知、定时触发通知。后面的多 Agent 协作，正是建立在这套运行时之上。
