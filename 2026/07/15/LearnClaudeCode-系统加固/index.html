Claude Code 系统加固：让 Agent 在真实工程里跑得久、跑得稳

2026-07-15- 2026-07-31
4.8k- 20m
课程笔记-学习Agent大模型Claude Code

本文是 Learn Claude Code 学习笔记的第二篇。第一篇讲了单 Agent 的六个核心机制（循环、工具路由、权限、Hook、待办、子代理）。这一篇讲怎么把「能跑」推进到「跑得久、跑得稳」：技能按需加载、四层上下文压缩、长期记忆、系统提示词动态装配、错误恢复。

为什么需要系统加固

上一篇结束时，Agent 已经有了循环、工具、权限、Hook、待办、子代理。但「能跑」不等于「跑得久、跑得稳」。五个具体问题：

  1. 项目规范全塞进 system prompt，每轮都带着 6500 行无关文档
  2. 对话越长 messages 越大，直到 API 返回 prompt_too_long
  3. 压缩会丢细节，用户说「用 tab 不要用空格」被简化成「用户有代码风格偏好」
  4. system prompt 是一整段硬编码字符串，改一处影响全局
  5. API 一抖（429 限流、529 过载、输出截断），Agent 直接崩溃

下面五章依次解决这五个问题。

技能加载：用到时再加载

问题

项目里有一套 React 组件规范、一份 SQL 风格指南、一份 API 设计文档，加起来 6500 行。最直接的想法是全塞进 system prompt。但 Agent 每轮调用 LLM 都要带着这 6500 行，不管当前是在改 CSS 颜色还是修 SQL 查询，99% 的内容跟当前任务无关，白白消耗 token。

两级加载

核心心智模型：先给模型一张菜单，等它点菜了再把菜端上来。

第一级只加载「技能目录」，告诉模型「你有哪些技能可用」，体量很小，常驻 system prompt。第二级才加载「技能正文」，只有当模型判断「我现在需要这个技能」并主动调用 load_skill 时，正文才通过 tool_result 进入对话。

最关键的一点：正文进入的是 messages，不是 system prompt。 这决定了它和上下文压缩天然衔接。

数据结构

SKILL.md。每个技能一个 Markdown 文件，开头是 YAML frontmatter：

SKILL_REGISTRY。一个字典，启动时一次性扫描填充，运行时只读不写：

content 字段在第一级加载时是不发的，等 load_skill 被调用才取出来。

实现

第一级：启动时扫描并注入目录。_scan_skills() 遍历 skills/ 下每个子目录，解析 SKILL.md 的 frontmatter，存进注册表。build_system() 把菜单拼进 SYSTEM prompt：

第二级：load_skill 工具。查找走的是 SKILL_REGISTRY 注册表而不是直接拼接文件路径，没有路径遍历风险：

技能内容作为一次 tool_result 进入当前 messages，后续调用会随消息历史一起携带，直到上下文压缩把它清理掉。需要时重新 load_skill 即可。

Claude Code 真实实现的差异

技能来源不是一个目录。CC 从多个来源加载：user / project / --add-dir 目录、legacy commands（.claude/commands/）、内置技能、MCP 远程技能、plugin skills、conditional skills（带 paths frontmatter，按文件路径激活）。

两级加载的精确实现。Catalog 预算约为上下文窗口的 1%，上限 8000 字符。Load 时 SkillTool 返回的 tool_result 展示文本只是 "Launching skill: {name}"，真正的技能内容是通过 newMessages 注入对话的，教学版把这两步合并了。

易错点

  1. 把技能正文写进 SYSTEM：违背两级加载的初衷，每轮都带全文，token 爆炸
  2. 用文件路径拼接加载：引入路径遍历风险，必须走注册表查找
  3. 以为加载一次就永远在：技能正文是 tool_result，会被 compact 清掉
  4. 目录里塞太多技能：目录本身也占 SYSTEM 空间，CC 给目录预算约 1% 上下文窗口

上下文压缩：四层压缩管线

问题

Agent 跑着跑着不动了。它读了 30 个文件、跑了 20 条命令，每条命令的输出、每个文件的全文全堆在 messages 列表里。上下文窗口是有限的，满了之后 API 直接拒绝：prompt_too_long。

核心设计原则

便宜的先跑，贵的后跑。 四层管线，前三层纯文本/结构操作，0 次 API 调用，每轮都跑。前三层都压不下去时，才动用第四层那次 LLM 调用。

L1：snip_compact，裁掉无关的旧对话

消息数超过 50 条时，保留头部 3 条（初始上下文）和尾部 47 条（当前工作），中间裁掉。关键边界条件：不能把 assistant(tool_use) 和后面的 user(tool_result) 拆开：

L2：micro_compact，旧工具结果占位

只保留最近 3 条 tool_result 的完整内容，更旧的替换为一行占位符：

L3：tool_result_budget，大结果落盘

单条 user 消息里所有 tool_result 加起来超过 200KB 时，按大小排序，从最大的开始落盘到 .task_outputs/tool-results/，上下文里只留 <persisted-output> 标记加前 2000 字符预览：

L4：compact_history，LLM 全量摘要

前三层全跑完了，token 仍然超阈值。三步流程：

  1. 保存 transcript：完整对话写入 .transcripts/，JSONL 格式
  2. LLM 生成摘要：把对话历史发给 LLM，要求保留当前目标、重要发现、已改文件、剩余工作、用户约束
  3. 替换消息列表：所有旧消息被替换为一条摘要

熔断器：连续失败 3 次后停止重试。

应急：reactive_compact

API 还是返回 prompt_too_long（413）时触发，比 compact_history 更激进，从尾部回退：

有重试上限（默认 1 次），再失败就抛异常。

顺序不能换

L3（budget）必须在 L2（micro）之前，因为 micro 会把旧的大 tool_result 替换成一行占位符，budget 必须在那之前把完整内容落盘，否则就永远找不回来了。

Claude Code 真实实现的差异

执行顺序。CC 源码中的真实顺序：applyToolResultBudget → snipCompact → microcompact → contextCollapse（教学版无）→ autoCompact。

read_file 的取舍。教学版 micro_compact 会把旧 read_file 结果也替换成占位符。CC 把 Read 也放进可 microcompact 的工具集合，但同时维护 readFileState：重复读取未变化文件时返回 FILE_UNCHANGED_STUB，compact 后再按预算恢复最近读过的文件内容（最多 5 个文件、每个 5K token、总预算 50K token）。

压缩 prompt 的硬性要求。CC 的压缩 prompt 开头就是 CRITICAL: Respond with TEXT ONLY. Do NOT call any tools.，模型需要先在 <analysis> 标签里理清思路，然后在 <summary> 标签里输出正式摘要。

易错点

  1. 顺序写反：先 micro 再 budget，会把旧的大结果先变占位符，再也没法落盘
  2. 把 tool_use 和 tool_result 拆开：API 会因为配对断裂报 400
  3. 以为 compact 是无损的：L4 是有损摘要，细节会丢，所以需要记忆系统来兜底
  4. 没有重试上限：reactive 或 compact 失败时一直重试会烧光 API 配额
  5. token 估算太粗：教学版用字符数近似，真实系统要换成精确 tokenizer

记忆系统：不丢的那一层

问题

s08 的 autoCompact 会把当前目标、剩余工作、用户约束写进摘要，但细节会丢失。「用 tab 缩进不要用空格」可能被简化成「用户有代码风格偏好」。而且新开一个会话，连摘要也没了。需要一层不参与压缩、跨会话保留的存储。

四个子系统

关键设计：索引常驻 SYSTEM prompt（可被 prompt cache 缓存），文件内容按需注入到当前 user turn（按 filename / description 匹配当前对话）。

数据结构

每个记忆是一个 .md 文件，YAML frontmatter 记录元数据：

type 字段分四类：user（用户偏好）、feedback（反复出现的反馈）、project（项目背景）、reference（常用入口和排查线索）。

MEMORY.md 索引一行一个链接，注入 SYSTEM：

实现

加载：两条路径。 路径一，索引常驻 SYSTEM。路径二，相关记忆按需注入，每轮用户请求开始时做一次 LLM side-query 选出相关的文件名（最多 5 条），再读文件内容临时注入。side-query 失败时降级到关键词匹配。

写入：每轮结束后提取。 用户不会每次都说「记住这个」，偏好散落在正常对话中。extract_memories() 在对话告一段落（stop_reason != "tool_use"）时运行：

提取前先检查已有记忆，避免重复。

整理：低频合并去重。 文件数达到阈值（默认 10）时触发，让 LLM 去重、合并矛盾、淘汰过时记忆。CC 把这个过程叫 Dream，实际有四层门控：时间间隔（距上次合并 >= 24 小时）、扫描节流、会话数（修改了 >= 5 个会话 transcript）、锁门控（没有其他进程正在合并）。

Claude Code 真实实现的差异

记忆选择用 LLM 不用 embedding。CC 用 Sonnet 本身来选：扫描 .memory/ 下所有 .md 文件（最多 200 个），把 name + description 列成清单，发给 Sonnet side-query「选出真正有用的记忆（最多 5 个）。不确定就不要选。」

提取通过 forked agent 执行。受限权限、skipTranscript: true、maxTurns: 5。还有重叠保护：如果主 Agent 已经写入了记忆文件，跳过提取。

存储位置：~/.claude/projects/<sanitized-git-root>/memory/。

易错点

  1. 把记忆正文塞进 SYSTEM：会让索引失去意义，token 爆炸。SYSTEM 里只放索引
  2. 提取器每轮都跑：只在对话告一段落时跑，避免无谓消耗 API
  3. 不做去重就写入：会写出大量重复记忆
  4. 整理触发太频繁：整理本身要调 LLM，频次过高反而浪费
  5. 混淆 Memory 和 session memory：Memory 跨会话，session memory 管当前会话的压缩续接

系统提示词组装：运行时拼出来

问题

从 s01 到 s09，system prompt 从一行变成了一大段硬编码字符串。换项目要重写整个 prompt，修改一处可能影响全局，每次请求都带全部内容。

分段 + 按需拼接 + 缓存

section（段落）。system prompt 被拆成一个个独立维护的小块，每块有自己的主题：

按需拼接。section 是否加载取决于真实状态（工具是否存在、文件是否存在），不是消息里的关键词：

缓存。上下文没变时（同一轮对话的多次 LLM 调用），重新拼接是浪费。用确定性序列化检测变化：

用 json.dumps 而不是 hash()：Python 内置 hash() 有进程随机化，且对 dict / list 报 unhashable type。

Claude Code 真实实现的差异

section 数量不固定。CC 大致分两类。静态 section（始终加载）：identity、system、doing_tasks、actions、using_tools、tone_style 等。动态 section（按状态加载）：session_guidance、memory、env_info、language、output_style、mcp_instructions、token_budget 等。

三层缓存。第一层 lodash memoize（会话中缓存）；第二层 section 注册缓存（/clear 或 /compact 时清除）；第三层 API 级缓存（通过 SYSTEM_PROMPT_DYNAMIC_BOUNDARY 分隔静态和动态部分，静态部分命中 global cache）。

总大小。标准交互模式下 system prompt 核心约 20-30KB 文本，CLAUDE_CODE_SIMPLE 模式约 150 字符。

易错点

  1. 用关键词猜测该加载哪个 section：应该看 context 的真实状态
  2. 用 hash() 做 cache key：进程随机化且对 dict / list 报错
  3. 把动态内容拼进静态段：会破坏 prompt cache
  4. 每轮都重新拼：同一 context 下重复拼接是浪费

错误恢复：错误不是终点

问题

三种最常见的故障模式：输出被截断（max_tokens 用完了）、上下文超限（压缩后还是太长）、临时故障（429 限流 / 529 过载）。一个不处理错误的 Agent 就像一个一碰就熄火的车。

四条恢复路径

核心设计：每条路径都有自己的次数上限和状态标志，不会无限重试。

RecoveryState

集中存放恢复状态的对象：

路径 1：输出被截断

模型话说一半 max_tokens 用完了。第一次发生时，直接把 max_tokens 从 8K 升级到 64K，重试同一请求（messages 不变）。如果 64K 还是不够，才保存截断输出并注入续写提示：

升级只有一次，续写最多 3 次，超过就退出。

关键：max_tokens 检查必须在 append 之前。如果先 append 再检查，截断输出就写回历史了，升级 token 后重试的就不是「同一请求」。

路径 2：上下文超限

s08 的四层压缩全跑过了还是超。触发 reactive compact，压缩后重试。但如果压缩过一次还是超限，只能退出，再压缩也不会变小。

路径 3：临时故障

429 和 529 统一走指数退避 + 抖动：min(500 x 2^attempt, 32000) + random(0~25%)。如果服务器返回 Retry-After header，优先用那个值。连续 3 次 529 过载，切换到备用模型。

Claude Code 真实实现的差异

十几种 reason / transition。教学版讲了 3 种最常见的，CC 实际有十几种，每轮 LLM 调用后都会判断。

续写提示原文：

流式错误处理。CC 的流式路径中，可恢复的错误（413、max_tokens、media error）在 streaming 期间被暂扣不展示，等 streaming 结束后才判断是否需要恢复。

Diminishing Returns 检测。Token budget 的「继续」不是无限的。当连续 3 次 continuation 且 token 增量 < 500 时，系统判断「继续也没有实质性产出」，停止 continuation。

易错点

  1. 不设重试上限：任何一条恢复路径没有上限都会烧光 API 配额
  2. max_tokens 检查放在 append 之后：截断输出写回历史，升级 token 失去意义
  3. reactive compact 反复触发：压缩过一次还是超限就该退出
  4. 退避不带抖动：并发请求会在同一时刻重试，加剧拥塞
  5. 把所有异常都当成可恢复：认证失败、模型不存在重试也没用，应该退出
  6. 续写提示太啰嗦：模型会复述上文浪费 token，必须明确「no apology, no recap」

小结：从「能跑」到「跑得稳」

机制 解决什么失败模式 核心设计
技能加载 system prompt 爆炸 两级加载，正文走 tool_result 不走 SYSTEM
上下文压缩 prompt_too_long 四层管线，便宜的先跑贵的后跑
记忆系统 compact 有损 + 跨会话失忆 索引常驻 SYSTEM，正文按需注入
系统提示词组装 prompt 硬编码难维护 分段维护，按真实状态拼装
错误恢复 API 报错即崩 四条恢复路径，每条有上限

这五章的共同主题是耐久性：让 Agent 在真实工程里长时间工作时不爆炸、不丢东西、不因 API 抖动而熄火。后面的多 Agent 协作，正是建立在这层稳固的单 Agent 之上。
