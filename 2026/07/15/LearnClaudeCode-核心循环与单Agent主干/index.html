Claude Code 的核心：所有机制挂在同一个循环上

2026-07-15- 2026-07-31
6.3k- 26m
课程笔记-学习Agent大模型Claude Code

本文整理自 Learn Claude Code 课程的学习笔记。课程把一个 Claude Code 式的编码智能体拆成 20 步，每步只往主循环里加一个机制。本文覆盖最核心的理念和前六步，从「会说话」到「会干活且干得稳」的单 Agent 主干。

核心设计哲学

机制很多，循环一个。

一个能长期工作的编码智能体，需要同时拥有工具分发与权限边界、Hook 扩展点、待办计划与任务图、技能/记忆/系统提示词组装、上下文压缩与错误恢复、后台任务与定时调度、多智能体协作、工作区隔离、MCP 外部工具接入。这些机制全都挂在同一个 while True 循环的不同位置上。循环本体从头到尾几乎没变，变的是循环周围的 harness 越来越完整。

循环的核心逻辑浓缩成一段话：

调用模型 → 检查响应里有没有 tool_use → 有就执行工具 → 把结果追加回 messages → 继续下一轮。

一句话总结：Agent 的核心不是「模型很聪明」，而是「系统持续把现实结果喂回模型」。

最小闭环：让模型「会干活」

问题在哪

语言模型本身只会「生成下一段内容」。它不会自己打开文件、运行命令、观察报错，更不会把工具结果再用于下一步推理。如果没有一层代码在中间反复做这件事，模型就只是一个「会说话的程序」，还不是一个「会干活的 Agent」。

关键名词

loop（循环）：这里不是「程序死循环」，而是「只要任务还没做完，系统就继续重复同一套步骤」。

turn（一轮）：最小版本里一轮通常包含四步：把当前消息发给模型；读取模型回复；如果模型调用了工具就执行工具；把工具结果写回消息历史。然后才进入下一轮。

tool_result（工具结果）：它不是随便打印在终端上的日志，而是「要重新写回对话历史、让模型下一轮真的能看见的结果块」。

state（状态）：主循环继续往下走时需要一直带着走的那份数据。最小版本里最重要的状态就是 messages、当前第几轮、这一轮结束后为什么还要继续。

最小心智模型

这条图里最关键的不是「有一个 while True」，而是：工具结果必须重新进入消息历史，成为下一轮推理的输入。 少了这一步，模型就无法基于真实观察继续工作。

最小实现

分五步走。

第一步：把用户请求放进 messages。

第二步：把消息历史、system prompt、工具定义一起发给模型。

第三步：把 assistant 回复写回历史。这一步非常重要，很多初学者只关心「最后有没有答案」，忽略了把 assistant 回复本身写回历史，下一轮上下文就会断掉。

第四步：如果模型调用了工具就执行。

第五步：把工具结果作为新消息写回去，下一轮重新发给模型。

为什么先接受 stop_reason == "tool_use" 这个简化

本章用 if response.stop_reason != "tool_use": return 完全合理。因为初学者在第一章真正要学会的不是所有复杂边界，而是三件事：assistant 回复要写回历史；tool_result 要写回历史；主循环要持续推进。

这只是第一层简化。更完整的系统不会只依赖 stop_reason，还会自己维护更明确的续行状态。这是后面要补的，不是一开始就要背下来的。

初学者最容易犯的错

  1. **把工具结果打印出来但不写回 messages**：模型下一轮根本看不到真实执行结果。
  2. 只保存用户消息不保存 assistant 消息：上下文会断层，模型越来越不像「接着刚才做」。
  3. **不给工具结果绑定 tool_use_id**：模型分不清哪条结果对应哪次调用。
  4. 一上来就把流式、并发、恢复、压缩全塞进第一章：主线会非常难学。
  5. 以为 messages 只是聊天展示：在 agent 里，messages 更像「下一轮工作输入」。

Agent Loop 的本质

Agent 之所以从「会说」变成「会做」，是因为模型输出能走到工具，工具结果又能回到下一轮模型输入。如果读者已经能凭记忆写出 messages -> model -> tool_result -> next turn 这条回路，这一章就达标了。

工具路由：加工具不改循环

问题在哪

只有 bash 时所有操作都走 shell。cat 截断不可预测，sed 遇到特殊字符就崩，每次 bash 调用都是不受约束的安全面。专用工具（read_file、write_file）可以在工具层面做路径沙箱。

关键洞察：加工具不需要改循环。

解决方案

dispatch map 是一个字典：{tool_name: handler_function}。一次查表取代任何 if/elif 链。

工作原理

消息规范化（normalize_messages）

教学版的 messages 列表直接发给 API，所见即所发。但当系统变复杂后（工具超时、用户取消、压缩替换），内部消息列表会出现 API 不接受的格式。需要在发送前做一次规范化。

API 协议有三条硬性约束：

  1. 每个 tool_use 块必须有匹配的 tool_result（通过 tool_use_id 关联）。
  2. user / assistant 消息必须严格交替（不能连续两条同角色）。
  3. 只接受协议定义的字段（内部元数据会导致 400 错误）。

规范化分三步：剥离内部字段（_internal / _source / _timestamp 等）；为没有配对 tool_result 的 tool_use 补一条占位结果（(cancelled)）；合并连续同角色消息。

在 agent loop 里每次 API 调用前运行：messages=normalize_messages(messages)。

关键洞察：messages 列表是系统的内部表示，API 看到的是规范化后的副本。两者不是同一个东西。

三个稳定点

这一章最重要的不是把完整工具运行时一次讲全，而是先讲清三个稳定点：

  • tool schema 是给模型看的说明
  • handler map 是代码里的分发入口
  • tool_result 是结果回流到主循环的统一出口

只要这三点稳住，就能在不改主循环的前提下新增工具。权限、Hook、并发、流式执行、外部工具来源这些层次当然重要，但都应建立在这层最小分发模型之后。

延伸：如果开始觉得「工具不只是 handler map」，是因为工具层后来还会长出权限环境、当前消息与 app state、MCP client、文件读取缓存、通知与 query 跟踪，最终更像一条「工具控制平面」。

权限系统：意图先过安全闸门

问题在哪

Agent 有多个工具了，文件工具受 safe_path 保护，但 bash 不受限制。让它「清理一下项目」，可能执行 rm -rf /。安全不能靠信任模型，要靠代码，在工具执行之前做判断。

三道闸门

循环完全保留，唯一变动是在工具执行前插入 check_permission()：每个工具调用经过三道闸门，顺序固定，硬拒绝优先，软询问次之，都没命中就放行。三道都没命中就直接执行，大部分日常操作走这条路。

闸门 1：硬拒绝表。先查，命中就返回阻止信息。

闸门 2：规则匹配。描述「什么时候需要问用户」。每条规则指定工具和检查条件。

闸门 3：规则命中后暂停等用户输入。

三道闸门串在一起，插在工具执行之前。循环体里只加了一行：

主循环不需要知道权限系统的存在，权限系统也不需要知道主循环的存在，它们通过「工具执行前拦截」这一个接口点连接。

Claude Code 真实实现的差异

教学版的三道闸门是刻意简化的。真实的 Claude Code 有几点重要不同：

PermissionResult 不是 3 种而是 4 种。CC 的权限结果有 4 个 behavior，教学版只覆盖了 deny/ask/allow。

验证阶段更复杂。CC 的工具调用经过多个阶段：Zod schema 验证 → validateInput() → backfillObservableInput() → PreToolUse hooks → 多层规则检查（整个工具被 deny → deny；被 ask → ask；工具自己的 checkPermissions()；内容相关 ask 规则；安全检查违规；bypassPermissions 模式 → allow；passthrough → ask）。

拒绝列表不是一个文件是 8 个来源。CC 没有单一的 deny list，权限规则来自 8 个来源（从低到高：user < project < local < flag < policy，加上 cliArg、command、session），高优先级来源覆盖低优先级。

isDestructive() 纯粹是 UI 展示用的。它在工具列表里显示 [destructive] 标签，不参与权限决策。

YoloClassifier（自动审批）。CC 的 auto 模式下不会每次都弹框，classifyYoloAction 把工具调用加对话上下文发给一个分类器 LLM 判断是否安全。先模拟 acceptEdits，再查安全工具白名单，最后才调分类器；连续拒绝太多次回退到人工审批。

权限冒泡。子 Agent 的 permissionMode 设为 'bubble'，权限弹窗冒泡到父 Agent 终端，而不是在子 Agent 里静默拒绝。

四个生命周期事件

四个事件覆盖一个完整的 agent cycle：

  • UserPromptSubmit：用户输入提交后、进入 LLM 前触发。可以拦截或修改输入。
  • PreToolUse：工具执行前（权限闸门之外的第二层拦截）。
  • PostToolUse：工具执行后，可以修改返回值或记录日志。
  • Stop：循环即将退出时触发。返回非 None 可以强制续跑。

Claude Code 真实实现的差异

Hook 事件不止 4 个而是 27 个。教学版只讲 4 个核心事件，因为它们覆盖了 agent cycle 的关键节点，其他 23 个都是同样的模式。

HookResult 有 14 个字段，教学版简化为「None = 继续，非 None = 阻止/续跑」。

关键不变式：Hook 的 allow 不能绕过 deny/ask 规则。这是 CC 权限系统最重要的安全设计：hook 返回 allow 时，仍要检查 settings.json 的 deny/ask 规则。即使用户的 hook 脚本说「允许」，settings.json 里禁用的工具仍会被阻止。

stopHookActive 防无限循环。Stop hook 产生 blockingError 时，循环带 stopHookActive: true 重入下一轮；后续迭代看到这个标志就不再触发。防止「模型自纠 → stop hook 报错 → 模型再自纠」的死循环。

hook_stopped_continuation。PostToolUse hook 返回 preventContinuation: true 时，query.ts 检测到后让循环退出。这是「hook 优雅地让 Agent 停机」，不是崩溃，是完成。

待办写入：让 Agent 学会做计划

问题在哪

给 Agent 一个复杂任务：「把所有 Python 文件改成 snake_case 命名，然后跑测试，修好失败。」Agent 改了 3 个文件，跑了个测试，发现 2 个失败，开始修。修着修着，它忘了最初是「改成 snake_case」，测试失败把注意力全吸走了。

对话越长越严重：工具结果不断填满上下文，系统提示的影响力被稀释。一个 10 步重构，做完 1 到 3 步就开始即兴发挥，因为 4 到 10 步已经被挤出注意力了。

Claude Code 真实实现的差异

CC 中有两套任务系统并存：

  • TodoWrite（V1）：简单的列表工具，数据在内存 AppState 中维护，退出清空。
  • Task System（V2 = s12）：文件持久化、依赖图、并发锁、ownership。

切换由 isTodoV2Enabled() 控制：交互式会话 V2 默认启用，非交互式（SDK）V1 默认启用；环境变量 CLAUDE_CODE_ENABLE_TASKS 可强制启用 V2。

Task System 相比 TodoWrite 的核心增量：文件持久化（tasks/{taskListId}/{taskId}.json）而非内存列表；blockedBy 依赖图而非平铺列表；proper-lockfile 并发安全而非无锁；四个独立工具（Create / Get / Update / List）而非一个；TaskCreated / TaskCompleted hooks 供外部系统集成。

子代理：子任务使用全新上下文

问题在哪

Agent 在修一个 bug，它读了 30 个文件来追踪调用链，中间聊了 60 轮。messages 列表涨到 120 条，其中大部分是「追踪调用链」的中间过程，和「修 bug」这个最终目标无关。这些中间过程占着上下文位置，让 Agent 越来越「健忘」。

换个角度：你修 bug 的时候，会「开一个新终端」来追踪调用链。追踪完了，终端关掉，结果写进笔记，回到原来的终端继续修 bug。Agent 也需要这个能力。

task 工具

调用 task 工具时 spawn 一个子 Agent，拥有全新的 messages[]，跑自己的循环，结束后只把摘要文本回传给主 Agent。对话上下文被丢弃，但文件系统的副作用（写文件、改文件、跑命令）保留在工作目录中。

子 Agent 的工具受限：有 bash / read / write / edit / glob，但没有 task，不能递归 spawn 新的子 Agent。子 Agent 的工具调用仍经过权限 hook，安全策略不因上下文隔离而跳过。

三个关键设计决策：dispatch 机制不变，task 工具通过 TOOL_HANDLERS[block.name] 分发；子 Agent 有独立的 SUB_SYSTEM 提示，明确要求「直接完成任务，不要再委派」；中间过程丢弃、只回传结论。

Claude Code 真实实现的差异

不是一种模式是三种。教学版只讲「全新的 messages[]」，CC 实际有三种执行模式（fresh messages、fork、teammate 等）。

Fork 模式：为了共享 Prompt Cache。Fork 模式不创建全新上下文，而是构造 cache-friendly 消息前缀，保留父 assistant message 并生成 placeholder tool results。目的不是隔离，而是让 Anthropic API 的 prompt cache 命中：父子 Agent 的 system prompt、tools、messages 前缀完全一致，API 端不需要重算。缓存命中的五个关键组件必须字节级一致：system prompt、tools、model、messages 前缀、thinking config。

Context Isolation 的精确粒度。子 Agent 不是完全隔离的：文件读取状态是共享的。UI 和通知的隔离程度取决于执行路径（sync / async / fork / teammate 各不同）。

递归 Fork 防护。教学版用「子 Agent 不给 task 工具」表达递归保护。真实实现更精细：isInForkChild() 检查对话历史中是否有 FORK_BOILERPLATE_TAG，有就拒绝；Agent 工具默认在所有 agent 的禁用集合里。

Permission Bubbling。Fork Agent 的 permissionMode: 'bubble' 意味着子 Agent 的权限弹窗冒泡到父终端。

Async vs Sync。教学版只展示同步子 Agent。CC 还支持异步路径：run_in_background: true 时异步启动，返回 { status: 'async_launched' } 立即给父 Agent，子 Agent 完成后通过通知机制告知父 Agent。

六个机制挂在哪里

回顾这一篇覆盖的六个机制：

机制 挂在循环的哪个位置 解决什么问题
Agent 循环 循环本身 把模型从「会说」变成「会做」
工具路由 工具执行环节 加工具不改循环
权限闸门 工具执行前 拦截危险操作
Hook 扩展点 循环各节点 不改源码也能扩展
待办写入 作为工具被调用 给模型外部记忆
子代理 作为工具被调用 隔离上下文、节省 token

注意一个规律：后面五个机制，有的是在工具执行前插入（权限），有的是在循环各节点插入（Hook），有的干脆就是作为一个工具被调用（待办、子代理）。不管挂在哪，循环本体始终是同一个 while True。

后面的章节会继续往这个循环上挂更多机制：技能按需加载、上下文压缩、长期记忆、系统提示词动态装配、错误恢复、后台任务、多 Agent 协作。但循环本身不变。
