Claude Code 多 Agent 平台与综合归位：从单兵作战到团队协作

2026-07-18- 2026-07-31
3.8k- 15m
课程笔记-学习Agent大模型Claude Code

本文是 Learn Claude Code 学习笔记的第四篇也是最终篇。前三篇讲了单 Agent 核心（循环/工具/权限/Hook/待办/子代理）、系统加固（技能/压缩/记忆/提示词/错误恢复）、任务运行时（持久任务/后台执行/定时调度）。这一篇讲多 Agent 协作平台（团队/协议/自治/隔离/MCP）和综合归位（全部机制挂回同一个循环）。

从单兵作战到团队协作

前三阶段结束时，系统始终是一个主 Agent 在做所有事：它再能拆任务、再会派子代理，子代理也是「做完就消失」的一次性外包。本章把这个单点骨架扩张成一张多 Agent 协作平台。

五个平台级能力依次接上：

  • 团队：让队友从一次性变成有名字、有邮箱、长期在线
  • 协议：让队友之间的协作从自由聊天升级成可追踪的结构化流程
  • 自治：让空闲队友自己扫描任务板认领工作，不靠 lead 手动分配
  • 隔离：让每个任务有自己的独立 git worktree 执行车道
  • MCP：让外部进程也能把工具接进 Agent 的工具池

团队与队友：长期在线的执行者

问题在哪

子代理的生命周期是写死的：创建 -> 执行 -> 返回摘要 -> 消失。这很适合一次性委派。但如果想让一个测试 Agent 长期待命、让两个 Agent 长期分工、让某个 Agent 在未来收到新任务后继续工作，就不够用了。系统需要的是：一批有身份、能长期存在、能反复协作的队友。

核心概念

teammate（队友）：一个拥有名字、角色、消息入口和生命周期的持久 Agent。它和子代理的根本差别不在名字，而在生命周期。

roster（名册）：团队成员列表，回答「现在队伍里有谁、每个人是什么角色、每个人现在是空闲、工作中还是已关闭」。教学版用 .team/config.json 持久化。

inbox（邮箱）：每个队友的收件箱。别人把消息发给它，它在自己的下一轮工作前先去收消息。教学版用 JSONL 文件：.team/inbox/alice.jsonl。

最关键的理解：每个队友都拥有独立的 messages、独立的 inbox、独立的循环。 共用 messages 会让上下文互相污染，共用变量喊话会把通信绑死在进程内部细节上。

三种委派机制怎么区分

机制 更像什么 生命周期 关键边界
subagent 一次性外包助手 干完就结束 隔离一小段探索性上下文
runtime task 正在运行的后台执行槽位 任务跑完或取消就结束 慢任务稍后回来，不是长期身份
teammate 长期在线队友 可以反复接任务 有名字、有邮箱、有独立循环

口语记法：subagent 适合「帮我查一下再回来汇报」，runtime task 适合「这件事你后台慢慢跑」，teammate 适合「你以后长期负责测试方向」。

团队协议：按规矩协作

问题在哪

s15 让队友之间可以互相发消息了。但如果所有事情都只靠自由文本，某些动作必须明确批准或拒绝，一旦多个请求同时存在就很难知道「这条回复对应哪一件事」。

核心概念

协议：双方提前约定好「消息长什么样、收到以后怎么处理」。

request_id：请求编号。让某个请求发出去以后有唯一身份，之后的批准、拒绝、超时都能准确指向这一个请求。

计划审批：某个队友想做高风险改动，可以先提计划等领导审批。底层和关机共用同一个请求-响应模板。

协议请求不是普通消息

邮箱里从 s16 起分成两类：

类别 适合场景 至少要带的字段
普通消息 讨论、提醒、补充说明 from / to / content
协议消息 审批、关机、交接、签收 type / request_id / from / to / payload

四种对象容易打结，按这张表记最稳：

对象 回答什么问题 典型字段
MessageEnvelope 谁跟谁说了什么 from / to / content
ProtocolEnvelope 这是不是一条结构化请求或响应 type / request_id / payload
RequestRecord 这件协作流程走到哪一步 kind / status / from / to
TaskRecord 真正的工作项是什么 subject / status / blockedBy / owner

协议请求不是任务本身，请求状态表也不是任务板。协议只负责「协作流程」，任务系统才负责「真正的工作推进」。

Worktree 隔离：每条任务一条独立车道

问题在哪

为什么 worktree_state 和 status 要分开

任务已经 completed，但 worktree 仍然 kept，这完全可能（做完了但还想保留目录给 reviewer 看）。所以任务状态和车道状态不能混成一个字段。

MCP 与插件：外部能力接回同一控制面

问题在哪

前面所有章节里，工具基本都写在 Agent 自己的 Python 代码里。但真实系统走到一定阶段，会很自然地想：能不能让外部程序也把工具接进来，而不用每次都改主程序？

最小心智模型

三件最重要的事

1. 有一个 MCP client：负责启动外部进程、发送请求、接收响应。

2. 有一个工具名前缀规则：

比如 mcp__postgres__query、mcp__browser__open_tab。一眼就知道：这是 MCP 工具、它来自哪个 server、它原始工具名是什么。

3. 有一个统一路由器：

关键不变量：MCP 工具虽然来自外部，但不能绕开权限。路由前要过共享权限闸门，路由后不论本地还是远程，结果都要转成主循环看得懂的统一 tool_result。

Plugin、MCP Server、MCP Tool 不要混成一层

三层记法：

  • plugin 负责「发现」（.claude-plugin/plugin.json 里的 mcpServers 告诉主程序怎么把 server 拉起来）
  • server 负责「连接」（MCP client 连接外部进程）
  • tool 负责「调用」（模型通过 mcp__server__tool 调用具体工具）

综合归位：全部机制挂回同一个循环

s20 做的事

前 19 章的教学方法是「每章只加一个机制」。这样适合学，但真实在跑的 Agent 不会只带一个机制运行。s20 不再新增机制，而是把所有组件归位到同一张图上。

完整 harness 的流程

读这张流程图时要注意三件事：

顺序是严格有意义的。UserPromptSubmit 在 LLM 之前（有机会修改用户输入）；cron 通知注入也在 LLM 之前（通知本质上是特殊用户消息）；context compact 在 system prompt 组装之前（压缩会改写 messages，而 system prompt 是基于组装时状态生成的）。

循环本身仍然是同一个结构。调用模型，检查响应里是否出现 tool_use，执行工具，把结果追加回 messages。

变化的是循环周围的 harness 变完整了。同一个 while True，现在它的每一侧都长出了多层次的支撑：输入侧有 hooks 和通知注入，模型调用侧有压缩和恢复，执行侧有权限、分发和后台，回流侧有 hooks 和通知回流。

两层计划并存

  • todo_write：当前会话内的轻量计划，保存在内存里。解决的是单个 Agent 在长任务里不漂移
  • task graph：跨会话、可依赖、可认领的任务文件。支撑的是团队协作

两者不是替代关系，而是互补。

两种委派并存

  • task：一次性子代理。独立 messages，跑完只回传摘要。解决「上下文隔离」
  • spawn_teammate：持久队友线程。通过 MessageBus 收发消息，能 idle 轮询任务板自动认领。解决「长期并行协作」

从 s01 到 s20，代码表面越来越复杂，但核心始终没变：

这五行就是 s01 写下的那个 loop。到了 s20，循环体的逻辑量和 s01 几乎一样多。变化的全在循环周围。

Claude Code 的复杂性不是「另一个 Agent 大脑」的复杂性，而是一个成熟 harness 的复杂性。模型负责判断和行动选择（这一层在 s01 就完成了）。harness 负责把环境、工具、权限、记忆、团队、外部能力组织好，让模型每次拿到的是干净的上下文、可用的工具、安全的边界（这一层从 s02 一直长到 s20）。

机制很多，循环一个。复杂的是 harness，不是 Agent 大脑。
